# Решения и их цена

| Решение | Причина | Ограничение и когда заменить |
| --- | --- | --- |
| dbt Core 1.12.3 и dbt-duckdb 1.11.0 | Учимся привычному Python-стеку dbt v1 с явным адаптером и lock | v2 уже существует; это закреплённая учебная конфигурация, не утверждение о самой новой версии |
| DuckDB 1.5.0 | Локальный движок без сервера, проверенная комбинация версий | Новая основная DuckDB 2.0 не нужна ради этого сценария; обновлять вместе с проверками |
| Два seed-источника | Наглядно видны данные до SQL, нет внешних доступов | Seeds подходят небольшим примерам, production ingestion должен быть отдельным |
| Суммы raw как varchar | Проверка дробных копеек до CAST; числовой CAST способен округлять | Парсер seeds сам нормализует часть представлений; это не побайтовый валидатор CSV |
| Предагрегация возвратов | Совместить зерно обеих сторон JOIN, не умножать цену заказа | Дополнительная модель; события остаются отдельно для расследования |
| Staging/intermediate как view, marts как table | Показать разницу логического представления и готового результата | Полный rebuild, без оптимизации объёма и SLA |
| Снимок после полного dbt build | Не показывать смешанную частично обновлённую базу | Не создаёт общую транзакцию SQL-моделей и не защищает нескольких писателей |
| Fingerprint входа и моделей | Старый JSON не выдаётся за результат изменённых CSV/SQL | Хэш не доказывает качество данных, не синхронизирует параллельные процессы |
| 1 поток | Маленький DAG легче читать и отлаживать | Это выбор понятности, не оптимальный режим больших витрин |
| Генератор отказывает на существующей папке | Сохраняет пользовательские учебные правки | Для нового сценария нужна отдельная копия проекта |

День возврата отсутствует сознательно: витрина показывает экономику заказов по дате
их оформления. Если нужен денежный поток по календарным дням, потребуется refund_date
и другой отчёт. Добавление такого поля без пересмотра смысла даты даст неверную аналитику.
