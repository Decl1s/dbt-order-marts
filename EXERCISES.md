# Пять заданий с проверкой ответа

Работай с копией сгенерированных CSV. После изменения всегда запускай build;
старый report без пересборки должен отказывать. Для каждого опыта восстанови базовый
набор в отдельной копии проекта, чтобы числа разных упражнений не смешивались.

1. **Измени частичный возврат.** В raw_refunds замени 2000 на 4000 у R0001.
   Ожидается refunded=10000, net=75000, 01.10 web=5000; gross остаётся 85000.
   Проверка: build успешен, report показывает эти значения.
2. **Верни заказ полностью.** Из исходного набора увеличь R0001 до 9000:
   вместе с R0002 это 10000. Ожидается net=70000, 01.10 web=0, оплаченных заказов
   всё ещё 5. Ещё одна копейка должна дать FAIL и запрет report.
3. **Найди fan-out.** В read-only исследовательском запросе соедини raw_orders
   с raw_refunds до группировки. Для O0001 строк станет 2, его цена при SUM даст
   20000 вместо 10000. Верный факт имеет 6 строк. Не удаляй предагрегацию из рабочего
   кода, пока не добавишь тест, обнаруживающий такое завышение независимо от витрины.
4. **Добавь средний net-чек.** В mart_daily_channel добавь
   `sum(net_cents)::double / count(*) as avg_net_cents`. В исходном наборе
   02.10 web: 35000 / 2 = 17500. Денежные суммы остаются целыми, среднее может быть
   дробным. Объясни, почему cancelled не должен увеличивать знаменатель.
5. **Добавь канал partner.** Скопируй O0006 под новым ID O0007, суммой 5000 и каналом
   partner. Сначала accepted_values должен отказать. Затем разреши partner в schema.yml
   и пересобери. Ожидается 7 строк факта, 6 оплаченных, 5 строк витрины, gross=90000,
   refunded=8000, net=82000; новая строка 02.10 partner=5000. Уникальный order_id обязателен.

Ответь словами: какие тесты проверяют данные, какой шаг исправляет зерно, почему
снимок не равен транзакции всей БД, что произойдёт после изменения SQL без build?
Сверь ответы с NOTES.md и своими run_results.json, а не только с зелёным кодом выхода.
