# Концепция: проверяемые аналитические витрины

22.10.2026, версия 0.1.0. Учебная задача: из заказов и частичных возвратов получить
экономику дня по каналам. Новый инструмент серии — dbt Core: SQL-модели, ref, DAG,
материализации, generic и singular data tests. DuckDB нужен как локальный движок.

Я ограничил проект одним аналитическим сценарием:
Linux/Windows, Python 3.12, две генерируемые таблицы, пять SQL-моделей, полный rebuild.
Источники синтетические; личные документы, контакты и платные платформы не используются.

Критерии: воспроизводимый net=77000; два возврата одного заказа не умножают gross;
повтор не дублирует строки; дубли ID, неизвестный заказ, плохой статус, превышенный
и дробный возврат отклоняются; после исправления входа результат восстанавливается.
Неуспешная сборка и изменённый вход блокируют показ прежнего снимка как актуального.

Результат — одна строка факта на заказ и одна строка витрины на дату/канал.
Возвраты относятся к дате заказа. Отменённый заказ остаётся в факте с нулевой gross,
но исключён из дневной витрины. Уникальный event_id возврата нужен для отличия
двух реальных частичных возвратов от повторённой записи. Дубли не исправляются молча.

Не входят: оркестратор, расписание, облако, API, web UI, инкрементальные модели,
общая транзакция всех моделей и конкурентные сборки. Следующие осмысленные шаги —
дата возврата и отдельный кассовый отчёт, валюты, независимая сверка с источником,
затем incremental с отдельными тестами запоздавших изменений.
